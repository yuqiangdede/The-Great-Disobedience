## 二、审查的具体任务

### 1. 前置核对

- 定位并实际读完本章唯一权威 Markdown 正文，核对文件身份、当前 Git 分支、现有未提交差异及正文版本。
- 确认本章自然段总数并建立可追踪段号；检查当前项目是否有 TXT 阅读副本、分卷合订本及官方导出工具，不以不存在的副本作为已经通过的验收项。
- 对本章相关的任务卡、卷纲、章纲、简写及人物/世界观约束进行必要核实。明确正文已发生事实与未批准计划的区别。
- 不修改本章以外的正式正文章节；如果复审发现相邻章问题，只记录证据，不在本次擅改相邻章节。

### 2. 全文深度审查（非机械扫描）

- 逐自然段开展真实语义阅读，登记应审、实审、遗漏段数和覆盖率。覆盖不满100%不得声称全文深审完成。
- 将剧情因果、人物动机、人物能力与限制、场景必要性、时空、世界观、关键事实、相邻章节连续性、伏笔与悬念分别核实。
- AI 味专项是最高优先级：按正式评分量表审阅自然中文与翻译腔、人物对白与各人声口、段落级叙事真实性、模板句式、冗余、机械表达及其他 AI 式写法。
- 真实裁决37项：每项按正式协议标注不明显、待复核、明显、证据不足或不适用。对命中项保留位置、短引文、上下文、实际阅读损害及最强反证；不得把单纯关键词/正则命中当成已成立问题。
- 对所有待复核项重新回到上下文查证并作出裁决；无法证实者保留待核实原因，不能直接忽略，更不能机械改写。
- 完成独立反方审阅；仅当当前工具真的支持独立委派时才宣称委派成功，否则明确为“单模型反证审查”，说明局限。
- 一条根因只计一次问题，不凭词频、第三方 AIGC 检测分数推断作者身份或直接扣分。

### 3. 评分与修订

- 按 `review-core.md` 的现行七维及语言55分内部五子项真实评分；初分、证据、反证和问题位置在修改前冻结。
- 对实质问题比较原文价值、阅读损害、最小候选修法及改动风险；**只有净收益明确为正才修改**。若没有可确认正收益的改法，允许零修改。
- 严格按 `review-core.md` 的当前阈值、最多五轮优化上限、复验与回滚要求执行；不得自行改阈值，不为达到轮次或提高分数硬改。
- 每轮修改后复核人物声口、自然中文、剧情事实、段落衔接、情绪与留白、受影响的前后文；负收益必须回滚并登记。
- 不为去 AI 味损害人物、情绪、故事因果、叙事节奏与作品风格；不改变重大既定情节；必须作者决定的实质冲突应记录并阻断不安全修改。

### 4. 工程同步与报告

- 按项目实际使用的正式工具，把已核实的 Markdown 源稿变更同步至**确实要求存在**的 TXT 阅读副本和分卷合订本；不要从 TXT 反向覆盖 Markdown，不要发明不存在的文件/工具。
- 真实运行适用的项目校验工具；记载命令、退出码、实际范围和结果。未执行、缺失、权限阻断或工具失败时如实说明，不能伪报通过。
- 在 `{{REPORT_PATH}}` 写入完整 Markdown 报告：实际阅读文件及版本、自然段覆盖证明、剧情/人物/设定裁决、独立反方或降级原因、初审和复审七维分数、语言五子项、37项逐项结果、问题证据与反证、改动差异、轮次/回滚、工程同步与验证、未解决问题和最终状态。
- 报告中分开判定：文学质量状态、AI 味专项状态、工程交付状态和独立反方状态。不能用总分高来推定专项通过。
- 若某项本章不适用，记录清楚原因；缺失关键依据或存在重大争议时不得伪称 PASS。

## 三、操作权限及隔离

- 只在当前 Git 分支工作，不创建工作树、分支或 PR；**不要执行 git commit、git push、git reset --hard、git clean**。
- 不覆盖当前工作区里与本章任务无关的已有改动；对他人已修改的相关文件，先核对差异，若无法安全合并则停止该写入并说明。
- 严禁虚构子智能体、工具调用、文件读写、评分改善或验收状态。
- 本章完成或遇到阻断时就退出本次会话；**不要启动下一章、不要自行调用 codex、不要修改批量脚本、不要把工作交给后台**。下一章由外部调度器启动另一独立会话。

## 四、最终机器可读结果

最终回复必须严格符合外部传入的 JSON Schema（不要再包 Markdown 代码块），并保证：

- `chapter_path`：精确填写 `{{CHAPTER_PATH}}`。
- `review_report_path`：精确填写 `{{REPORT_PATH}}`；报告必须真实落盘。
- `status`：只有全部适用步骤真实完成、无阻断问题、文学质量允许通过、37项专项通过、工程交付达到项目要求时才是 `PASS`；需作者裁决或证据不足填写 `NEEDS_AUTHOR`；执行失败或文件/工具/验收不完整填写 `FAILED`。
- `workflow_complete`：只有完整审查、真实修订/零修改裁决、复验及适用工程校验都实际完成才为 `true`。
- `ai_review_status`：使用 `通过`、`不通过` 或 `待核实`。不能将总分高当作专项通过。
- `initial_score` / `final_score`：没有可靠实际评分则填写 `null`，不能造分。
- `optimization_rounds`：实际落笔或回滚的轮次数，零修改为0。
- `changed_files`：只填写实际修改的仓库相对路径。
- `unresolved_issues`：只填写仍未解决的问题，严禁隐去阻断问题。
- `summary`：简要说明本章真实完成内容、重要修改、回滚、同步与未完成原因。

这是一项实际的完整审稿与自动改稿任务，不是撰写执行计划或仅给修改建议。立即开始读取项目文件并执行。
